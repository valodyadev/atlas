# 0006. iOS modularised as Swift packages, with a generated Xcode project

- **Status:** Accepted
- **Date:** 2026-11-21

## Context

Two problems that compound as an iOS codebase grows.

First, `.pbxproj`. It is a generated-looking file that is nonetheless edited by
the IDE, it conflicts on almost every parallel branch, and its conflicts are
unreviewable. On a team of more than two it becomes a recurring tax paid in
confusion.

Second, a single app target. Everything can import everything, so layering is
aspirational; incremental builds get slower in proportion to total code, not
changed code; and unit tests need a simulator, which means minutes instead of
seconds.

## Decision

**All code lives in a local Swift package** (`ios/Packages/AtlasKit`) with one
target per layer and one target per feature:

```
AtlasCore            logging, telemetry contract, clock, environment
AtlasNetworking      API client, error shape, retries        -> AtlasCore
AtlasDesignSystem    tokens, components, state views         -> AtlasCore
AtlasFeatureUsers    one feature                             -> the three above
```

Dependencies are declared in `Package.swift`, so a feature importing another
feature is a compile error rather than a code-review conversation.

The app target is a shell: entry point, composition root, navigation,
Keychain access. Everything else is a package.

**The `.xcodeproj` is generated by XcodeGen from
[`ios/project.yml`](../../ios/project.yml) and is not committed.** Build
settings live in `ios/App/Config/*.xcconfig`, which are plain text and
reviewable.

Targets declare `macOS` alongside `iOS` so the package builds and tests on a
bare Swift toolchain — which is what makes the fast CI gate possible.

## Alternatives considered

| Option | Why not |
| --- | --- |
| Committed `.xcodeproj`, one app target | The two problems above, permanently |
| Tuist | Solves the same problem well and does more (caching, generated graphs). Heavier to learn and adds its own version to pin. Worth revisiting at a much larger size |
| Separate `.xcodeproj` per module | Pre-SPM solution; more project files, same merge problem |
| iOS-only targets | Would force every unit test onto a simulator and lose the sub-two-minute CI gate |

## Consequences

**Good**

- No `.pbxproj` conflicts, ever.
- Layer violations are compile errors.
- `swift test` runs the whole unit suite in seconds, with no Xcode, no
  simulator and no code signing — so CI gives feedback in under two minutes.
- Incremental builds recompile a feature, not the app.

**Bad / accepted costs**

- `xcodegen generate` must be run after pulling a change that adds files, and
  the error when you forget ("file not found") is not self-explanatory.
- Declaring `macOS` means genuinely UIKit-only code must live in the app shell
  or behind `#if os(iOS)`.
- Contributors need XcodeGen installed; `make bootstrap` and `make doctor`
  cover that.

**What this makes harder later**

- Anything that requires hand-editing project structure in Xcode's UI: the
  change has to be expressed in `project.yml` instead, and the mapping is not
  always obvious.

## Revisit when

The package graph gets large enough that build times matter more than
simplicity — that is the point to evaluate Tuist and its caching.
